## Why this matters

`npm audit` reports 11 vulnerabilities (7 high). Several affect code that runs
at runtime, not just dev tooling: `ws` (the WebSocket engine behind
`@hono/node-ws`, which serves `/ws`) has an uninitialized-memory-disclosure and
a memory-exhaustion DoS advisory; `hono` itself has multiple high advisories;
`@mariozechner/pi-coding-agent` (the agent SDK, always loaded) has an auth.json
write race that can expose stored provider credentials and a predictable
temp-path local-privilege-escalation. Because pragents is "local-first,
remote-ready" (AGENTS.md), the WebSocket and Hono advisories become real the
moment the server is exposed beyond localhost. Patching these is low-effort and
high-value.

## Current state

Reachable-at-runtime high-severity advisories confirmed via `npm audit --json`
at commit `867809f`:

- `ws` — Uninitialized memory disclosure; Memory exhaustion DoS. Pulled in by
  `@hono/node-ws` (declared in root `package.json:10` and `server/package.json:13`).
  **Reachable**: the server serves a live WebSocket at `/ws`.
- `hono` — CORS wildcard-with-credentials reflection; `serve-static` path
  traversal on Windows; several others. Declared `server/package.json` (`"hono": "^4.0.0"`).
- `@mariozechner/pi-coding-agent` — auth.json write race (credential exposure);
  predictable temp extension path (LPE on shared hosts); Markdown-export XSS.
  Declared `server/package.json` (`"@mariozechner/pi-coding-agent": "^0.73.0"`).
- `undici`, `form-data` — high, but transitive and not directly reached by
  pragents' own code (no direct multipart upload route; no direct undici use).
  Patch them via the lockfile bump but they are lower urgency.

Dev-only advisories (`vite`, `esbuild`, `@babel/core`, `launch-editor`) affect
only the `web/` build/dev server, never the shipped server. Patch them too, but
they do not gate a remote deployment.

Verification baseline: `cd server && npx tsc --noEmit` is currently green, and
`cd web && npx tsc --noEmit && npx vitest run` is green (411 tests). Server
`npm test` requires a matching Node native build — see plan 002; if server tests
fail with a `NODE_MODULE_VERSION` error, that is the pre-existing native-module
mismatch, not something this plan introduced.

## Scope

**In scope** (the only files you should modify):
- `package-lock.json` (regenerated by npm)
- `package.json` — only if a manual version bump is needed for `hono` / `@hono/node-ws`
- `server/package.json` — only if `hono` or `pi-coding-agent` need an explicit range bump
- `web/package.json` — only if `vite` needs an explicit range bump

**Out of scope** (do NOT touch):
- Any application source under `server/src/` or `web/src/`. This plan is
  dependency hygiene only — no code changes.
- The `overrides` block in root `package.json` pinning `monaco-editor@0.53.0` —
  leave it exactly as is; it exists to resolve a prior advisory.
- Downgrading `@mariozechner/pi-coding-agent` below `^0.73.0`. The API surface
  pragents uses (`server/src/agents/runtime/`) targets 0.73+; a downgrade is a
  STOP condition, not a fix.

## Steps

### Step 1: Record the baseline

Run `npm audit` and save the count. Note how many high-severity advisories exist
and which packages. This is your before/after reference.

**Verify**: `npm audit` → prints "11 vulnerabilities (2 low, 2 moderate, 7 high)"
or a similar count. Record the exact numbers.

### Step 2: Apply non-breaking fixes

Run `npm audit fix` (NOT `--force`). This bumps within existing semver ranges
and regenerates `package-lock.json`.

**Verify**: `npm audit` → high-severity count is lower than the Step 1 baseline.
`git diff --stat` shows only `package-lock.json` changed (and possibly nothing
in the manifests).

### Step 3: Manually bump any advisory that `audit fix` could not resolve within range

For each remaining high-severity advisory on `ws`, `hono`, `@hono/node-ws`, or
`@mariozechner/pi-coding-agent`, check whether a patched version exists inside a
minor bump. If so, widen the range in the appropriate `package.json` (e.g.
`"hono": "^4.0.0"` → `"hono": "^4.12.25"`) and run `npm install`. Do **one
package at a time** and re-run typecheck after each.

If a patched version requires a **major** bump (breaking change), STOP and report
which package and which advisory — do not force a major upgrade blind.

**Verify** after each bump: `cd server && npx tsc --noEmit` → exit 0, and
`cd web && npx tsc --noEmit` → exit 0.

### Step 4: Confirm the app still builds and web tests pass

**Verify**:
- `cd web && npx vitest run` → 411 tests pass (or more; none fail).
- `cd web && npm run build` → exit 0.
- `cd server && npx tsc --noEmit` → exit 0.

### Step 5: Final audit

Run `npm audit` once more. The remaining advisories (if any) should be only
dev-only or unreachable-transitive ones that require a major bump — list them in
your report with a one-line reachability note each.

**Verify**: `npm audit` → no **reachable-runtime** high advisories remain on
`ws`, `hono`, or `pi-coding-agent`; any leftover highs are documented.

## Maintenance notes

- Do not run `npm audit fix --force` casually — it will pull major versions of
  React, Vite, and the pi SDK and break the build. Prefer scoped manual bumps.
- After plan 002 lands (CI + Node pinning), `npm audit` should run in CI so new
  advisories surface on PRs instead of during a security review.
- The `undici`/`form-data` transitive highs are patched by the lockfile bump but
  remain worth watching if a direct HTTP-client or multipart-upload feature is
  added later — at that point they become reachable.
- Reviewer should scrutinize the lockfile diff for unexpected major bumps and
  confirm the `monaco-editor` override survived untouched.
